## Устройство формы

Форма отправляет JSON на `POST /api/landing/contact` на том же домене. Получатель
фиксирован: **info@chanly.ru**. Имя, почта и вопрос входят в текст письма,
адрес посетителя — в `Reply-To`. После принятия письма SMTP-сервером обработчик
возвращает `{ "delivered": true }`. Только этот ответ очищает форму.
При сбое введённое сохраняется, сообщение остаётся рядом с кнопкой.

[server.py](../deploy/contact/server.py) работает отдельно от статических файлов
Vite. Выпуск или откат `landing/current` его не перезапускает. Обработчик
выпускается отдельно; сама сборка сайта его не устанавливает.

## SMTP REG.RU

Для почты на хостинге REG.RU используются `mail.hosting.reg.ru`, порт `465`
и SSL/TLS. Логин — полный адрес ящика, пароль — пароль ящика.
Сверьте приобретённую услугу с [инструкцией REG.RU](https://help.reg.ru/support/hosting/nastroyka-pochty-regru/nastroyka-pochty-i-pochtovykh-kliyentovv/nastroyka-pochtovykh-kliyentovv):
у другого почтового продукта настройки могут отличаться.

На сервере создайте `.env` по [.env.example](../deploy/contact/.env.example).
Без заполненного `SMTP_PASSWORD` сервис не запускается. `SMTP_FROM` должен
совпадать с адресом ящика для входа. `CONTACT_ALLOWED_ORIGINS` содержит точные
адреса сайтов через пробел, без завершающего `/`.

Файл `.env` хранится только на сервере с правами `600`, исключён из Git
и Docker build context. Пароль не должен попадать в переменные `VITE_*`.
Compose читает `.env` в формате `raw`: значения записываются без кавычек,
символы `$` и обратные слеши в пароле сохраняются без подстановок.
Для этого требуется Docker Compose 2.30 или новее; на стенде проверена 5.7.0.

## Включение на текущем сервере

1. Скопируйте содержимое `deploy/contact/` в `/opt/maxim-dev/landing-contact`.
   В этом каталоге создайте и заполните `.env`, ограничьте права доступа.
2. Выполните там `docker compose up -d --build`. Образ использует Python 3.13
   и стандартную библиотеку, работает без root. Сервис подключён к существующей
   Docker-сети `edge`, публичного порта нет.
3. Добавьте обработчик в маршруты нужного сайта Caddy **до выбора документа
   лендинга или приложения**, сохранив действующий Basic Auth:

   ```caddy
   handle /api/landing/contact {
       reverse_proxy chanly-landing-contact:8091 {
           header_up -Authorization
           header_up X-Real-IP {remote_host}
       }
   }
   ```

   Caddy обязательно перезаписывает `X-Real-IP`: по нему ограничивается частота.
   Маршрут должен быть доступен гостю без авторизации кабинета. Для работы
   на двух доменах добавьте маршрут в оба сайта и оба origin в `.env`.
4. Проверьте конфигурацию штатными `caddy validate` и `caddy reload`.
   После включения SMTP отправьте согласованную контрольную заявку, проверьте
   входящие `info@chanly.ru` и ответ через `Reply-To`. `/healthz` проверяет
   только процесс, не доступность SMTP.

Для нового окружения до заполнения `.env`, запуска сервиса и настройки Caddy
отправка недоступна. Текущий dev-стенд уже настроен.

## Проверки

```sh
python3 -m unittest deploy.tests.test_contact
npm run test -- tests/components/ContactSection.spec.js tests/components/contactDelivery.spec.js
```

Тесты используют поддельный SMTP и локальный HTTP-сервер. Настоящие письма
не отправляются. Проверяются принятие письма, отказ SMTP, origin, согласие,
ограничения полей и частоты, сохранение данных и повторная попытка.
Лимиты: пять попыток с одного IP и 100 суммарно за час, не более четырёх
одновременных SMTP-отправок. Лимиты хранятся в памяти одного процесса
и сбрасываются при перезапуске. Тексты заявок и SMTP-ошибок не журналируются.
